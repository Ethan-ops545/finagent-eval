# finagent-eval

[![CI](https://github.com/Ethan-ops545/finagent-eval/actions/workflows/ci.yml/badge.svg)](https://github.com/Ethan-ops545/finagent-eval/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

一个最小的**金融研究 Agent** + 一套**能自证有效的评测**。

Agent 的部分不难：调工具取财报、算几个指标、写一段结论。
难的是下一个问题——**这段结论凭什么可以信**。

一个 Agent 可以读文档、调工具、做计算、然后用很流畅的语言给出结论。
即使其中某个数字、某步计算、某条依据是错的，它读起来一样自洽、一样权威。
所以这个项目的重心不在 Agent，而在评测：把「结论是否可被独立验证」变成可判定的事。

而评测本身也要被验证。所以跑起来第一眼看到的不是分数，是**自检**：

```
## 一、自检（先看这个）

### 1. 检查器是否可信
- 误报：**0**（无）
- 已知故障检出：**7 / 7**

| 注入的故障 | 说明 | 期望检出 | 结果 |
|---|---|---|---|
| `wrong_formula`    | 同比少减 1，自洽地算错        | `value_mismatch`    | ✅ |
| `value_typo`       | 公式对但数值抄错              | `self_inconsistent` | ✅ |
| `unit_swap`        | 数值对但单位标错              | `unit_mismatch`     | ✅ |
| `ungrounded_input` | 引用了从未取过的一期          | `ungrounded`        | ✅ |
| `lookahead_input`  | 用了 as_of 之后披露的数据     | `lookahead`         | ✅ |
| `dropped_metric`   | 该给的结论没给                | `missing_metric`    | ✅ |
| `text_contradicts_value` | 数值全对，但叙述说反了  | `text_value_mismatch` | ✅ |

### 2. 参考实现是否与基准同步
- 参考实现在基准上的 findings：**0**（同步）

### 3. 判断项是否有效
- 参照答案的 rubric 失分：**0**（无）
- 已知表述缺陷检出：**2 / 2**

| 注入的缺陷 | 说明 | 结果 | 确定性检查报了什么 |
|---|---|---|---|
| `unqualified_verdict` | 下了定论却不交代行业语境     | ✅ | **全绿** |
| `one_sided_solvency`  | 只用盈利端判断偿债，漏掉杠杆 | ✅ | **全绿** |
```

检出率不到 100%、或者出现误报时，后面的分数一律不看。一套抓不到已知错误的评测，
给出的高分只说明它没在看；一套会误报的评测，报出来的问题也不值得查。

**「误报」是在参考报告上测的，不是在 Agent 的输出上测的**（`evalkit/oracle.py`）。
参考报告直接按基准声明的公式与输入复算而来，构造上必然正确，完全不经过 Agent。
拿 Agent 的输出测误报是循环论证——Agent 对不对本身是未知数，它上面报出的 finding
究竟是误报还是 Agent 真错了，分不出来。故障注入同样打在参考报告上，
这样"能不能检出已知故障"就不依赖被测对象的好坏。

第 2 节是另一件事：mock 是本基准的参考实现，它应当拿满分。拿不满分说明**基准与实现
脱节**（典型情形：基准新增了指标，而 `METRIC_RECIPES` 没补配方），这要修的是实现，
不是检查器。

第 3 节验的是 rubric。**不被检验的 rubric 只是几句好听的话**，所以它同样要过
"参照答案零失分 + 注入已知缺陷必须失分"这一关。注意那两个缺陷**一个数字都没改**，
确定性检查在它们面前全绿——光靠复算抓不到"把需要行业语境的判断说成确定结论"，
而在投研场景里这种错误比算错一个小数点贵得多。

三节分开是有实际意义的，退出码就按它分：`1` 检查器有问题（分数不可用，修 `evalkit`），
`2` 实现没跟上基准（分数真实，补配方），`3` 判分器有问题（确定性那半可用，
修 `judge`/rubric）。

## 跑起来

不需要任何 API key，默认就能跑完整流程：

```bash
pip install -r requirements.txt
python scripts/make_synthetic_data.py     # 生成基准数据
python run_demo.py                        # 跑基准，出记分卡
python -m pytest tests/ -v                # 29 项测试
```

接真实大模型：

```bash
pip install anthropic
export ANTHROPIC_API_KEY=...
python run_demo.py --provider anthropic
```

产物在 `runs/`：`scorecard.md`（记分卡）、`<task>.report.json`（结构化报告）、
`<task>.trace.jsonl`（全链路追踪）。

`run_demo.py` 的退出码按**评测器自己是否可信**来定，不是按 Agent 考了多少分——
自检没过就返回非零，方便挂 CI。

## 它是怎么工作的

### 1. Agent 不许交一段散文

最终输出必须是结构化报告，每条结论标明类别（`finagent/schema.py`）：

| 类别 | 含义 | 怎么验 |
|---|---|---|
| `computed` | 算出来的 | 必须给出公式与每个变量的**字段引用**，评测器独立复算 |
| `retrieved` | 直接取的 | 必须给出唯一的字段引用，评测器回原始数据比对 |
| `judgment` | 判断性表述 | 无法复算，走 rubric 单独打分 |

字段引用是全项目的地址格式，也是"证据可追溯"的物理基础：

```
NOVA.income.FY2024.revenue
NOVA.market.2025-04-15.close_price
```

报告里的每个数字都挂着这样一串地址，评测器才有办法回到原始数据重算一遍。

### 2. Agent 不许心算

任何算术都必须调 `compute` 工具，而且**不能直接传数字**——
只能提交「公式 + 每个变量对应的字段引用」，由工具回到快照取原始值再算
（`finagent/tools.py`）。

这一条设计带来的直接后果：算术错误被彻底消掉了。`compute` 的返回值永远等于
"这个公式配这组输入"的正确答案。Agent 还能犯的错就只剩两种——**选错公式**、
**选错输入**——而这两种评测器都查得出来。这就是 JD 里说的"确定性逻辑兜底"
落到代码上的样子。

求值器走 AST 白名单，不用 `eval()`（`finagent/calc.py`）。
公式字符串是大模型生成的，属于不可信输入；直接 eval 等于把任意代码执行权交出去。
测试里专门有一条断言它拒绝 `__import__`、`open`、推导式等构造。

### 3. 七类检查，各对应一种真实失效

`evalkit/deterministic.py`：

| 检查 | 抓的是什么 |
|---|---|
| `missing_metric` | 该给的结论没给（答非所问） |
| `value_mismatch` | 与按基准公式独立复算的结果不符 |
| `self_inconsistent` | 数值与它自己声明的公式算出来的不符（算完了，写报告时写了别的数） |
| `unit_mismatch` | 数值对，单位标错（"13.1" 到底是 13.1% 还是 13.1 倍） |
| `ungrounded` | 引用了 Agent 从未取过的数据 |
| `lookahead` | 用了 `as_of` 之后才披露的数据 |
| `text_value_mismatch` | 给人读的那句话与给机器读的那个数不一致 |

其中 **`ungrounded` 只能靠追踪查**。光比对答案永远发现不了它——
一个没有任何依据的结论，完全可能碰巧是对的。所以 `finagent/trace.py`
记的不是日志，它是评测的一部分：每次取数工具调用都登记"本次让 Agent 看到了哪些字段"，
报告里任何超出这个集合的引用，一律判为捏造。

`lookahead` 同理。取数工具**不会**替 Agent 挡住晚于 `as_of` 的数据——这是有意的，
真实系统里数据库并不知道你的研究基准日。把前视做成"工具层封死"，评测就永远
检不出这类错误，而它恰恰是投研场景里最常见、也最贵的一种。

`text_value_mismatch` 补的是另一个方向的盲区：前六条验的全是**机器读的字段**
（value / formula / inputs / unit），可**没有人会去读 JSON 里的 value**——
研究员读的是 `text`。所以一条「数值完全正确、叙述说反了」的结论能通过前六条全部检查，
而人拿到手里就是错的。这也是大模型的经典失效：生成叙述句和生成结构化字段是两条路径。

这条检查有两个刻意的设计：一是**先剔除期间记号再抽数字**，否则「FY2024」里的 2024
会被当成数值，干净报告立刻误报；二是**方向词只对变化量类指标校验**——
「毛利率 38.8%，较上年下滑」说的是变化不是水平，拿它去校验正负号会误报。
后者是本条检查明确的边界，写在代码注释里。

### 4. 可复算的部分和判断的部分，分开计分

`evalkit/judge.py` 只处理确定性评测管不了的东西——表述有没有说清依据、
有没有超出数据作推断。这些没有唯一答案，只能按 rubric 打分。

两部分**不合成一个总分**。一旦合并，一段写得漂亮的结论就能把一个算错的数字盖过去。

## 设计取舍

**为什么不用 LangChain 之类的框架。**
这个项目要讲清楚的恰好是工具调用循环内部发生了什么——哪一步该记账、
哪一步该拦截、哪些信息必须留到评测阶段。框架会把这些包起来。
主循环手写只有 60 行（`finagent/agent.py`），换来的是每个环节都能插进检查。
生产环境里用框架是另一回事，那时的取舍不一样。

**为什么基准用合成数据。**
评测集需要**精确已知的真值**。真实财报有重述、有口径调整、有授权问题，
会把"模型错了"和"数据本身有歧义"混在一起，评测就不可判定了。
这三家公司是虚构的，生成脚本在仓库里（`scripts/make_synthetic_data.py`），
数字内部严格自洽——资产负债表恒等式有测试兜着。

想在真实数据上验证同一套契约，用 `scripts/fetch_real_snapshot.py`
把 yfinance 的数据抓成同构快照，Agent 与评测器一行都不用改。
但真实数据不进基准集，理由同上。

**为什么 mock provider 不是大模型。**
`MockProvider` 是脚本化的假模型（`finagent/llm.py`），按固定策略调工具、按固定配方出报告。
它存在的唯一理由是：**评测器本身要能被测试，就必须有一个行为完全可预测的被测对象。**
拿真模型去测评测器，两边都在动，测出来的东西说明不了任何问题。
它不是在假装会做金融分析。

**为什么故障注入是主程序的一部分，不是测试的附属品。**
一套评测器交付时，读它的人第一个该问的问题不是"Agent 考了多少分"，
而是"这套评测能不能发现错误"。所以自检这一节印在记分卡的最上面，
并且决定整个程序的退出码。

## 目录

```
finagent/
  schema.py      输出契约：Claim / Report，三类结论的定义与校验
  calc.py        AST 白名单求值器（不用 eval）
  snapshot.py    快照读取与字段引用解析
  tools.py       五个工具 + 工具声明（Anthropic tool-use 格式）
  trace.py       全链路追踪：每次工具调用暴露了哪些字段
  agent.py       手写的工具调用循环（含轮次上限）
  llm.py         provider 抽象：MockProvider / AnthropicProvider
evalkit/
  deterministic.py  七类确定性检查
  oracle.py         参考报告：按基准声明直接复算，构造上必然正确
  judge.py          rubric 打分（启发式 / 大模型两种实现）
  faults.py         七种确定性故障 + 两种表述缺陷的受控注入
  runner.py         跑基准、出记分卡
benchmark/tasks.yaml  基准任务集（含每个指标的正确公式与输入）
data/snapshots/       合成财报快照
tests/                29 项测试：零误报、零漏报、判分器可信、两类失败可分辨、求值器安全性、数据自洽
```

## 已知边界

写在前面，省得看的人自己去猜：

- 任务集只有 3 个标的 × 1 类问题（单期经营概览）。**这不足以支撑任何关于
  "Agent 能力"的一般性结论**，它验证的是这套契约与检查链路成立。
- `HeuristicJudge` 是关键词规则，粗糙是刻意的。它现在**过了自检**（参照答案零失分、
  两种已知缺陷全检出），但这只说明它能抓到这两种缺陷，不说明它会评文章。
  换一种说法绕过关键词就能骗过它。真要评表述质量得用 `LLMJudge`，
  而 LLM 打分本身的一致性没有在这里测过。
- 没有做多智能体、没有做记忆、没有做工具编排。单 Agent、单轮任务。
- `lookahead` 只检查"数据发布日 ≤ as_of"。真实的前视偏差还有更隐蔽的形式
  （比如用了事后才知道的行业分类），这套检查抓不到。
- `text_value_mismatch` 只查每条结论自己的 `text`，**不查 `summary`**。
  摘要里说反了、或摘要与某条结论互相矛盾，目前抓不到——那需要跨结论推理。
  方向词的校验也只覆盖变化量类指标，理由见上文。
- 合成数据的分布是人工设定的，不反映任何真实行业的统计特征。
